# 同模型自纠正与双视角复核

SpecFlow 的复核节点现在默认执行两次使用相同模型配置的新会话：一次从原始需求检查覆盖，一次从反例和失败路径尝试推翻结论。两个会话读取同一份冻结材料，不共享对方的报告、摘要或修复结论。仅当两个报告都通过且历史阻塞问题完成复验，当前审核对象才能获得复核认证。

这减少上下文与结论锚定，并以工程条件阻止部分错误继续传播。同一模型仍可能出现相同的知识或推理错误；本次没有用真实供应商评测证明语义纠错率提升，也不保证消除共同偏差。

## 执行与门禁

1. 每次点击复核创建新的 `groupId`，固定需求正文、每份需求附件、项目章程、审核对象、上游产物链、候选代码和验证证据。
2. `coverage` 会话先从原始需求重建预期，再检查覆盖、假设与边界、上下游一致性、验证充分性。
3. 服务保存第一份报告，在同一事务内排队第二个 `adversarial` 尝试。第二个尝试使用新的会话 ID、独立的提示与同一批材料，逐项构造反例。
4. 两份报告必须分别列出全部准则、原文引证、具体反例与检查结果。引文必须真实存在于冻结材料；每份非空材料均须被核对。每个历史问题必须单独返回修复结论。
5. 缺失报告、缺失显式 `findings`、漏项、伪引文、失败、未知、未检查反例、未修复 blocker 或输入过期都阻塞。两份报告不能跨批次或跨版本拼接。

`@accepted` 输入是参考材料。只有复核节点声明的当前候选产物获得认证；设计复核不会顺带给规格背书。只有参考材料、没有审核对象的节点会在流程编译时被拒绝。

## 问题进入修订，而不是随版本消失

历史发现按工作项和目标产物保留。改措辞、重导入、创建新版本或替换代码哈希不会让旧 blocker 自动失效。生产者重跑时会收到问题、位置、原失效场景与当前待修订文档；生产者发现上游错误时，其结构化发现也会保存并阻塞流程。

只有两个新会话都基于当前版本明确证明修复，服务才关闭历史问题并记录复验尝试。单次测试通过不能手动关闭语义上的阻塞发现。修订仍由现有阶段重跑触发；本次没有增加无限自动修复循环。

## 候选代码和证据

代码及收敛复核读取候选工作空间。服务提供真实补丁、新增未跟踪文件正文、代码哈希所对应的验证命令和实际输出。命令配置、最新证据、候选、需求、章程或任一上游版本改变都会使旧审核失效。

实现与收敛产物保存 `candidateId` 和 `codeHash`。导入、手工编辑和应用外修改会保留既有依赖及代码依据，不能靠换一份报告为不同代码背书。缺少候选依据的旧代码报告需要重新生成。

## 恢复、兼容与资源边界

- 排队且尚未调用底座 `prepare` 的第二个尝试可在重启后安全派发；已经取得执行身份的尝试只查询、恢复原身份，不重复发出工具执行。
- 启动中断且没有取得身份时，服务明确阻塞，允许创建新尝试。过时尝试不能修改新尝试的节点状态。
- 历史记录、已保存的文档、冻结流程定义和模型配置保留。仅旧 `reviewed` 布尔标志不能满足新的双视角门禁，需要重新复核；`requireReview: false` 的显式设置仍按原有配置处理文档接纳。
- 当前仍使用批准的 Apache Maka 0.2.0 Runtime Host，不引入新 harness 或供应商切换。
- 每个复核步骤增加一次模型调用；恢复及重试会产生各自的尝试记录。延迟与费用取决于实际连接。
- Maka 0.2.0 单次阶段文本最多 48 KiB UTF-8。超限会在创建模型会话或派发前明确报错，要求缩小输入；完整审核材料不会被静默截断。补丁和新增文件也有显式大小限制。
