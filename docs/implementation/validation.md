## Maka 的实际接入验证

固定版本为 `maka-agent@0.2.0-dev.78.20261010`。通过官方 npm registry 安装到仓库的 `.tools/maka`，不要求修改全局安装。

真实 Maka Host 已在 Windows 上通过本地 HTTP 协议夹具验证：

1. Host 启动、握手、连接目录查询与连接创建。
2. 显式连接和模型目标的会话创建、Turn 派发与终止身份读取。
3. 实际会话记录的分页装配与最终模型文本读取。
4. 通过 `tool_search` 激活 SpecFlow 工作区扩展，再真实修改隔离文件。
5. 只读阶段无法激活写入工具，文件保持原样。
6. 澄清问题经过 `interaction.query / answer` 对应的正式交互链路。

夹具返回固定的模型协议响应，验证真实 Host 和工具路径，不代表真实模型质量或真实供应商兼容性已通过。用户已明确选择先完成应用，随后补齐真实连接。

## Windows 接入决策

固定版本的内置受控文件 worker 在当前 Windows 环境返回 `requires_bypass`。实现没有自动启用全局 Bypass，而是加入 `specflow.workspace` Host 扩展：

- `SpecFlowRead`、`SpecFlowList`：访问当前应用工作区内的源码。
- `SpecFlowWrite`：按现有内容哈希修改文件，拒绝只读调用、越界链接、设备路径、`.git`、`.specflow` 和 `.env`。
- `SpecFlowQuestion`：使用底座已有的用户问题机制。

这些是应用限定的文件工具，不是操作系统沙箱。工程验证命令在本机运行，应使用可信仓库。

插件包安装和组合状态写入还存在 Node 在 Windows 上无法打开目录句柄进行 fsync 的问题。`packages/maka-adapter/compat.ts` 对固定版的两个文件做有哈希约束的兼容处理：

| 文件 | 原始 SHA-256 |
| --- | --- |
| plugin-package-store.js | 3933ad2335b9f61aea4bbcc4f4207ca94c6ef506ba51c50ed19e20ba6fe63cb6 |
| plugin-composition-store.js | f833da06a01141f924a59754b690d523fe43ae1b87a6460a9e10908fec5cb68c |

文件内容和操作日志仍会刷新；目录元数据的断电持久性不作保证。版本或代码哈希不符时拒绝自动修改。实际修改记录保存到 Maka 包内的 `specflow-compatibility.json`。

Git 命令使用临时 `core.autocrlf=false`，避免默认 Windows 换行转换使已验证内容与集成内容不一致，不修改用户的全局 Git 配置。

`npm test` 覆盖领域规则、本地 API、隔离工程链、失败路径、恢复身份、工作区边界和真实 Maka Host 协议。

| 方案验收项 | 证据 |
| --- | --- |
| AC01 导入与复用产物 | API 导入保持候选，文档接纳与阶段消费按版本验证 |
| AC02 流程依赖与门禁 | 删除复核、重排输入、删除验证节点均被拒绝 |
| AC03 阶段模型选择 | 尝试固化目标，Maka 本地协议验证显式目标；真实供应商待补 |
| AC04 模型重试 | 新尝试和产物版本保留旧记录，流程快照不被改写 |
| AC05 验证失败 | 实际失败命令阻塞任务和接纳 |
| AC06 复核发现 | 未决问题形成阻塞发现，文档不可接纳 |
| AC07 上游变更 | 文档更新及应用外编辑使下游结果过期 |
| AC08 并发编辑 | 版本条件拒绝旧编辑；浏览器保留本地草稿与原版本 |
| AC09 过期证据 | 修改候选代码后，旧复核和测试不能放行 |

| AC12 停止与恢复 | 假后端验证停止确认与新恢复身份；真实长任务恢复待供应商验收 |
| AC13 Git 冲突 | 工作项分支被外部提交改变时拒绝接纳 |
| AC14 记录导出 | 导出版本、身份、证据和决策，不包含应用会话凭据 |
