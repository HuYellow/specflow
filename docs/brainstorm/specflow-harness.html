A

产品目标、范围与架构决策

A.1 产品定位

面向个人和小团队，围绕本地 Git 仓库组织 AI 软件开发。 开发者组合步骤，选择各阶段的 API 和模型，并共同审阅产物。

Spec Kit 与 speckit-codex-flow 提供方法启发。 应用自行定义工程阶段、产物格式与验收规则。 这些方法通过应用机制实现，不要求用户安装对应 skill。

本方案采用已有执行底座，产品的工程规则与流程仍保持独立。

A.2 本版确定的设计方向

决策 本版方案 原因
产品形态 本地 Web 工作台 + 本地工程服务 便于验证独立产品与执行边界
执行底座 以 Maka Runtime Host 为首个接入目标 复用 Agent 循环、工具、事件和恢复
接入方式 独立控制台 + 薄适配器 工程模块通过明确接口访问底座
模型选择 每个阶段或任务独立解析连接与模型 配置可替换，运行身份可追踪
上下文交接 使用固定版本的产物与代码基线 减少跨模型历史迁移的依赖
数据归属 工程状态归 SpecFlow，执行事实归 Maka 两层各自维护明确的事实来源
首版流程 可组合的串行步骤 先验证完整工程链，再扩展控制流
文档存储 Markdown 在仓库，工程元数据在本机 文档可编辑、可版本管理

Maka 作为计划中的执行底座，须先通过 P0。 P0 未通过时，暂停后续接入依赖，记录阻塞项。 不将“源码存在接口”视为“实际链路已验证”。

A.3 产品需求与首版交付

编号 需求 MVP 交付
R01 自由组合工程步骤 增删、替换、重排串行节点并校验输入
R02 共同管理文档产物 编辑、评论、差异、负责人和接纳记录
R03 自由组合 API 与模型 项目、流程、节点三级配置与新尝试
R04 执行真实代码开发 派发代码任务，取得补丁和工具记录
R05 门禁与独立复核 检查证据、处理发现、人工接纳
R06 需求变更后的影响追踪 按产物版本标记下游结果过期
R07 中断恢复与可追踪运行 保存执行身份，重连核对原运行
R08 本地与异步协作 Git 产物交换、评论和复核记录

MVP 交付一套规格驱动模板，并允许从已有文档开始。 多人实时编辑、远程执行和复杂流程分支进入后续版本。

MVP 的执行范围是仓库修改与本地验证。 代码集成到工作项分支需要用户接纳。 合并主分支、推送和部署由用户另行触发。

B

系统架构、模块与数据归属

B.1 运行拓扑

本地工程服务监听回环地址。 工作台通过本地 API 和事件订阅访问工程状态。 与 Maka 的协议和权限交互集中在适配器内。

Maka Host 保持自身执行状态的写入权威。 SpecFlow 使用公开接口，不直接修改 Maka 的数据库。

B.2 模块边界

模块 职责 主要输出
ProjectService 仓库发现、工程规则、工作项和基线 Project、WorkItem
WorkflowCompiler 校验节点顺序、输入引用和必需门禁 固定版本的可执行定义
WorkflowEngine 就绪判断、阶段推进、暂停和修订 NodeRun、状态事件
TaskScheduler 实现节点内的任务依赖与串行派发 TaskRun、任务结果
ContextAssembler 装配规则、产物、代码和复核发现 ContextManifest
ArtifactService 候选产物、版本、差异和接纳 ArtifactRevision、Decision
GateEvaluator 执行结构、证据和接纳检查 GateResult、阻塞原因
VerificationRunner 执行项目配置的验证命令 VerificationEvidence
ExecutionBackend 统一执行底座接口 运行身份与规范化状态
MakaBackend Host 连接、会话、执行和交互适配 Maka 身份与事件引用

VerificationRunner 是工程验收专用模块。 它运行固定命令清单，记录退出码和代码版本。 模型执行中的测试活动另作工具事实保存。

P0 若确认 Host 有适合的确定性验证通道，可以复用该通道。 否则使用本地受控进程执行器，并限制其职责为工程验证。 这一选择记录为 P0 的交付决策。

B.3 数据和凭据归属

数据 所有者 SpecFlow 的访问方式
模型连接、模型目录、供应商凭据 Maka Host 查询可用目标，保存身份引用
模型消息、工具结果、执行终止事实 Maka Host 订阅、查询和按引用读取
流程、门禁、任务与接纳决策 SpecFlow 工程数据库与版本化定义
文档和代码 Git 工作空间 版本快照、候选差异和接纳
验证命令及确定性验证报告 工程配置与验证器 版本化命令、报告和结果记录

SpecFlow 不复制供应商密钥到流程文件。 Maka 当前凭据存储方式由其实现决定。 本方案不将其描述为已经采用操作系统密钥链。

B.4 建议技术栈与代码组织

界面采用 React 与 TypeScript，工程服务采用 Node.js 24 系列。 工程状态使用 SQLite，流程定义使用 YAML，产物保留 Markdown。 具体依赖版本在 P0 通过后固定。

Maka 内部包标记为 private。 适配器使用经验证的 Host 客户端或协议边界。 不假设存在可直接安装的稳定 Runtime SDK。

specflow/
  • apps/
    • web/流程、产物、任务和运行界面
    • server/本地 API、调度和数据库
  • packages/
    • domain/流程、任务、产物与门禁契约
    • workflow-engine/编译、调度和状态转换
    • execution-contract/执行底座接口
    • maka-adapter/Host 协议与交互适配
    • artifact-service/快照、差异和接纳
    • verification-runner/确定性工程验证
  • templates/
    • spec-driven/默认工程流程与阶段指令
  • docs/
    • brainstorm/方案和底座评估

本地 MVP 已实现对应职责。首版工作流、任务和门禁集中在 apps/server/src/service.ts，产物管理位于 artifacts.ts；后续可按该结构拆分包。

C

流程定义、任务执行与状态机

C.1 首版节点类型

类型 作用 是否使用模型
agent 仓库分析、规格、设计、拆任务和实现 使用阶段模型
review 独立检查产物，输出结构化发现 使用复核模型和独立上下文
verify 运行预配置的构建、测试或检查 无需模型决定命令
gate 检查输入、证据与接纳条件 执行确定性规则
human 等待澄清、编辑或接纳 保存人工决策

MVP 按节点序列执行，并维护产物依赖图。 产物依赖图允许多个输入来源，但不能形成环。 条件分支、并行 Join 和自动修订回路进入后续版本。

模板可要求独立复核和必需验证。 用户自由组合步骤时，编译器提示缺少的工程条件。 硬门禁在工程服务执行，阶段提示词表达执行目标。

C.2 默认规格驱动模板

工程阶段 输入 输出 放行条件
仓库分析与需求规格 项目规则、需求、仓库基线 spec.md、未决问题 内容完整，必要澄清已解决
工程设计 已接纳规格、代码基线 plan.md、设计决策 复核发现已处理，用户接纳
任务拆解 已接纳规格与设计 tasks.md、任务清单 任务有 ID、依赖与验收条件
代码实现 就绪任务、相关设计与代码 候选补丁、实现说明 对应任务验证与复核通过
验证与收敛 候选代码、规格和任务 验证证据、对齐报告 必需检查通过，产物版本一致
接纳代码 已复核候选与基线 工作项分支的新检查点 用户确认，基线未变化

默认模板在各 AI 阶段产出后执行独立复核。 规格和设计等待人工接纳。 实现阶段按任务串行执行，最终代码等待人工接纳。

已有 Markdown 可以导入为候选输入。 通过结构检查与接纳后，流程可以从所需阶段开始。

C.4 阶段状态与完成语义

底座返回 completed，表示模型执行已经结束。 阶段仍需经过产物检查、验证、复核和接纳。

运行状态、产物接纳状态和依赖新鲜度分别记录。 执行失败、工程阻塞与产物过期也分别展示。

情况 状态处理 后续动作
API 或工具执行失败 execution = failed 保存结果，允许创建新尝试
未解决复核发现 gate = blocked 处理发现后重新检查
人工未接纳 acceptance = pending 等待明确决策
上游产物更新 freshness = stale 禁止放行，选择重检或重跑
执行提交结果不明 execution = reconciling 查询原身份，不盲目重发
用户请求停止 记录停止意图 等待底座确认终止

C.5 任务调度与修订

任务具有稳定 ID、依赖、范围和完成条件。 任务清单接纳后，TaskScheduler 按依赖串行派发。 每个 TaskRun 使用独立会话和固定输入清单。

任务补丁通过验证与复核后，形成候选分支检查点。 后续任务使用该检查点作为基线。 这些检查点仍属于候选改动，最终接纳后才进入工作项分支。

失败尝试的补丁和工具记录保留用于诊断。 重试基于明确的检查点创建新尝试。 模型更换也创建新尝试，不覆盖原记录。

首版由用户触发修订和重跑。 后续自动修订策略需声明最大尝试次数、时间和预算。

C.6 门禁规则

门禁 确定性检查 语义检查与决策
输入门禁 必需版本存在，输入哈希一致 是否存在未解决的需求问题
产物门禁 文件、任务 ID 和必需字段完整 独立复核对应内容
实现门禁 任务就绪，工作空间和配置可用 设计决策是否足以执行任务
验证门禁 必需命令成功，证据对应候选代码 用例是否覆盖验收目标
接纳门禁 基线一致，无阻塞发现，证据未过期 用户接纳该版本

语义检查输出可定位的发现，并标记严重程度。 发现处理必须绑定复核目标与后续证据。 项目可允许带理由接纳部分警告，并保存决策。 必需验证失败和执行结果不明时，保持阻塞。

D

Maka 适配、阶段模型与恢复协议

D.1 执行底座契约

ExecutionBackend 隔离 Maka 的协议和版本差异。 工程引擎仅使用应用契约，不读取底座内部对象。

ExecutionRef 保存 backend、rootId、sessionId、turnId 和 runId。 创建前尚不存在的身份保持为空，并随确认结果补齐。 这些身份通过 ExecutionBinding 关联阶段 Attempt。 恢复产生新的 Turn 或 Run 时，追加身份绑定并保留原关联。

start 返回的是启动回执，不是工程验收结果。 observe 可以返回暂态进度；query 用于核对确定状态。 最终放行以底座确认的终止事实和工程证据为准。

D.3 模型配置与覆盖规则

解析顺序为：节点覆盖 → 流程角色 → 项目默认。 角色声明执行目标、指令、输出要求和所需能力。 模型目标引用 Host 的连接身份与模型标识。

创建会话时，适配器传入显式 modelTarget。 运行前保存最终解析结果与配置哈希。 每个阶段尝试都能查看实际目标与模型用量。

场景 本版行为
规格和实现使用不同 API 两个阶段分别创建会话并选择连接
同一角色更换模型 使用相同输入版本创建新尝试
修改流程中的模型配置 影响新运行，已启动尝试继续使用原配置
连接被删除或模型不可用 阻塞启动，并显示配置原因
模型能力不满足节点 编译或启动检查失败

首版关闭自动备用模型。 用户手动切换后，保留旧结果和费用记录。 后续备用策略需验证能力、权限、上下文和预算匹配。

连接配置和凭据通过 Maka 管理。 SpecFlow 的模型选择界面展示 Host 的已配置目标。 首版不新增一套供应商适配与登录实现。

D.4 阶段输入与上下文

FrozenInput 包括以下内容：

  • 工程规则、阶段指令和模板版本。
  • 已接纳输入的 ArtifactRevision 与内容哈希。
  • 代码基线、选定文件及上下文清单。
  • 对应任务、未决问题和复核发现。
  • 输出路径、产物契约与运行限制。

Maka 创建接口没有任意 system prompt 或工具白名单字段。 阶段指令可通过输入内容表达。 细粒度工具和目录限制须在 P0 验证，必要时采用小型 Host 扩展。 权限或隔离能力不足时，相关节点不能静默降级运行。

D.6 中断、重试与预算

派发前，工程服务持久化 Attempt 和启动意图。 客户端启动请求也带有幂等键和工程状态版本。

断线后使用同一个 rootId、sessionId 和 turnId 查询。 只有底座明确证明未提交，才允许重试相同派发。 结果不明时保留 reconciling，避免重复执行写入任务。

恢复调用先取得 ResumePlan，再检查基线和输入版本。 核对工作空间时，也考虑原执行已确认的文件修改。 无法区分工具写入与外部编辑时，保持待核对状态。 底座可能拒绝恢复，此时展示原因并允许创建新尝试。 换模型重试与恢复原运行使用不同动作。

阶段交互使用底座的 interactionId 和正式回答通道。 用户回答被确认后，才继续显示执行状态。 产物接纳是 SpecFlow 的决策，不冒充底座权限回答。

maxSteps 使用已验证的底座能力约束工具步数。 时间上限触发停止请求，并等待终止确认。 费用预算按实际用量检查，阻止后续派发。 正在处理的请求可能超出估算，费用上限属于尽力约束。

E.1 文档产物协议

类型 文件示例 内容要求

阶段输出文件与产物清单共同接受检查。 产物清单记录类型、路径和输入引用。 路径相对候选工作空间解析，并检查实际文件。 缺少清单或必需文件时，保持工程阻塞。

需求到代码的关联可由模型建议。 关联记录的存在本身不构成已覆盖验收的证明。

E.2 编辑、复核与接纳

编辑文档生成新版本，并保留旧版本。 评论绑定 ArtifactRevision 与段落位置。 段落改变后，旧评论保留并提示定位可能失效。

候选产物先保存为不可变快照。 接纳记录绑定内容哈希、复核结果、操作者与理由。 部分接纳会形成一个新的完整版本，再重新检查门禁。

多个进程修改文档时，使用 expectedRevision 和内容哈希检查。 冲突响应返回当前版本与候选差异。 不允许用旧版本直接覆盖当前内容。

人工接纳和文件写入使用持久化操作日志。 先保存意图与基线，再原子替换文件，最后提交接纳记录。 崩溃恢复根据目标哈希核对已完成的动作。 文件系统写入与 SQLite 提交不假设为同一个事务。

E.3 上游变更后的失效传播

InputBinding 记录每次尝试消费的产物版本。 上游版本更新后，沿依赖关系标记下游结果 stale。

已运行步骤的输入不会被原地替换。 其结果可以继续保留，但不能作为新版本的已验收结果。 用户选择重检或创建新尝试，再恢复后续推进。

修改流程定义创建 WorkflowRevision。 WorkflowRun 固定自己的流程版本与工程规则版本。 首版对变更后的流程创建新运行，并复用明确接纳的输入。

E.4 Git 工作空间与代码接纳

对象 工作空间策略
Project 用户的源仓库，记录已选择的 Git 基线
WorkItem 独立工作项分支与工作空间
CodeCandidate 基于检查点的候选分支与 worktree
TaskRun 首版串行使用候选工作空间，记录自己的基线

首版采用干净、已提交的基线。 发现用户未提交改动时，阻塞准备并说明如何选择基线。 应用不自动重置、提交或删除用户现有改动。

任务间的候选检查点用于继续开发和故障定位。 最终代码接纳前，再次核对基线、复核目标与测试证据。 集成到工作项分支时，记录 Git 操作与结果身份。 出现冲突则保留候选，等待人工处理。

测试证据绑定实际代码内容哈希与环境清单。 验证前后内容改变，证据立即标记为过期。 旧测试成功不能放行新的补丁。

只读复核和工作空间隔离属于 P0 必验能力。 可用的插件或策略扩展需保持在适配器边界内。
